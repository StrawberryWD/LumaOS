LumaOS 5.0 - LMFS (Luma File System) 超级块设计文档

DAY29 (第二月 · 第5周 · Day 29):
  "设计 LMFS 超级块布局（位于 LBA 1）：魔数 0x4C4D4653、版本号、
   inode 数量、数据块数量、inode 位图起始 LBA、数据块位图起始 LBA。"

  这是 LMFS（LumaOS 自己的专属文件系统）的第一份设计文档，产出是
  "文档"而不是代码——Day 1~28 的 FAT12/16/32 是在"解析别人已经定好的
  格式"，超级块布局是别人焊死的，我们没有设计空间；从今天起 LMFS
  是我们自己从零定义的格式，所以第一步不是写 .c/.h，而是先把"磁盘上
  第 X 个字节是什么意思"想清楚、写下来，Day 31 起才照着这份文档去写
  真正的 lmfs.h/lmfs.c。这也是为什么第 5 周的任务分成两天纯设计
  （Day 29 超级块、Day 30 inode）——磁盘格式一旦上线不好改，多花一天
  想清楚，比写完代码才发现漏了字段划算。

================================================================================
一、"LBA 1"指的是谁的 LBA 1？—— 卷内相对地址，不是磁盘绝对地址
================================================================================

计划里写"位于 LBA 1"，容易被误读成"整个磁盘镜像的绝对第 1 扇区"。
但看现有的 build.sh 磁盘布局：

    绝对 LBA 0        mbr.bin    （512 字节引导记录）
    绝对 LBA 1 ~ 5    loader.bin （第二阶段引导器，5 个扇区）
    绝对 LBA 6 ~ 261  kernel.bin （内核本体）
    绝对 LBA 2500     tests/fat12-bpb.bin   （FAT12 BPB 测试卷）
    绝对 LBA 5000     tests/fat12-with-file.img （FAT12 测试卷）
    绝对 LBA 10000    tests/fat16-with-file.img （FAT16 测试卷）
    绝对 LBA 30000    tests/fat32-with-file.img （FAT32 测试卷）

如果把 LMFS 超级块焊死在"磁盘绝对 LBA 1"，会直接砸在 loader.bin
头上——这是致命冲突，不能这么做。

本项目里 FAT12/16/32 测试卷早就示范过正确的做法：每个卷从"自己的
LBA 0"开始独立编号（fat12-with-file.img 内部的簇/扇区号都是相对
自己卷首算的），卷被 dd 到磁盘哪个绝对位置（5000、10000、30000...）
是"挂载/嵌入时"才决定的外部信息，跟卷内部的格式定义无关。

所以本文档对"LBA 1"的解读是：**LMFS 卷自己的 LBA 0 是这个卷的引导
扇区/保留扇区，LBA 1（即卷首 + 1 个扇区偏移，512 字节 × 1 = 偏移
0x200 字节处）放超级块**——这是卷内相对地址，完全独立于这个卷将来
被烧录到磁盘哪个绝对 LBA。等 Day 85~91 做"安装到硬盘"、或者更早
测试阶段需要把 LMFS 卷嵌入到 build.sh 生成的镜像里时，会像
fat32-with-file.img 那样另选一个不冲突的绝对 LBA（沿用本项目一贯
"挑一个远离已用区域的安全位置"的方法），到时候会在 build.sh 里
写清楚并更新本文档，但那是实现阶段（Day 31 之后）的事，不影响今天
的格式设计。

    LMFS 卷内部布局（本阶段设计范围）：

        卷内 LBA 0   : 保留扇区 / 卷引导扇区（本阶段占位，暂不使用，
                        为将来"卷本身也能被引导"之类的扩展留空间）
        卷内 LBA 1   : 超级块（lmfs_superblock_t，本文档的主题）
        卷内 LBA 2 ~ : inode 位图 / 数据块位图 / inode 表 / 数据区
                        （起始位置由超级块里的字段给出，具体划分
                        等 Day 30 定完 inode 结构、块大小之后再确定）

================================================================================
二、超级块结构 lmfs_superblock_t（设计稿，非最终代码）
================================================================================

    typedef struct {
        /* --- Day 29 要求的核心字段 --- */
        uint32_t magic;             /* 0x4C4D4653 = ASCII "LMFS"        */
        uint16_t version_major;     /* 主版本号，当前 = 1               */
        uint16_t version_minor;     /* 次版本号，当前 = 0               */
        uint32_t inode_count;       /* 本卷 inode 总数                  */
        uint32_t data_block_count;  /* 本卷数据块总数                   */
        uint32_t inode_bitmap_lba;  /* inode 位图起始 LBA（卷内相对）   */
        uint32_t data_bitmap_lba;   /* 数据块位图起始 LBA（卷内相对）   */

        /* --- 为未来升级预留的字段（详见第三节） --- */
        uint32_t feature_compat;    /* 兼容特性标志：旧驱动可忽略        */
        uint32_t feature_incompat;  /* 不兼容特性标志：不认识就拒绝挂载  */
        uint32_t feature_ro_compat; /* 只读兼容标志：不认识就只挂只读    */

        uint8_t  reserved[476];     /* 预留字节，补齐到 512 字节整扇区  */
    } lmfs_superblock_t;            /* sizeof == 512（1 个磁盘扇区）    */

字节偏移表（从超级块自己的起始处，即卷内 LBA 1 的第 0 字节算起）：

    偏移量        大小   字段
    ------------  -----  --------------------
    0x000 (0)     4      magic
    0x004 (4)     2      version_major
    0x006 (6)     2      version_minor
    0x008 (8)     4      inode_count
    0x00C (12)    4      data_block_count
    0x010 (16)    4      inode_bitmap_lba
    0x014 (20)    4      data_bitmap_lba
    0x018 (24)    4      feature_compat
    0x01C (28)    4      feature_incompat
    0x020 (32)    4      feature_ro_compat
    0x024 (36)    476    reserved
    ------------  -----  --------------------
    总计          512    == 1 个 512 字节扇区（1 LBA）

    为什么整体大小刚好凑成 512 字节：超级块本来就整个占用卷内 LBA 1
    这一个扇区，读写它天然就是"读 1 个扇区、写 1 个扇区"，不需要
    再处理"结构体只用了扇区的一部分，剩下半截是垃圾数据"这种情况；
    reserved 数组既是对齐手段，也是第三节说的"给未来功能留空间"。

================================================================================
三、字段详解
================================================================================

magic (0x4C4D4653)
    'L'=0x4C 'M'=0x4D 'F'=0x46 'S'=0x53，ASCII 拼出 "LMFS"。跟
    fat_common.h 里 fat_detect_type() 认 BS_FilSysType 字符串是同一
    个思路：挂载时先读这 4 个字节，对不上就说明这不是 LMFS 卷（或者
    卷头损坏），直接拒绝挂载，不往下走，避免把无效数据当文件系统用。

version_major / version_minor
    拆成两个 uint16_t 而不是一个 uint32_t，是因为"主版本变了"和
    "次版本变了"驱动要做的事完全不同：次版本升级（比如 1.0 -> 1.1）
    通常只是加了新的可选特性，老驱动大多还能正常读写；主版本升级
    （1.x -> 2.x，比如本文档"关于 LMFS"milestone 一节说的 v2.0 引入
    Extents）往往意味着磁盘布局的根本变化，老驱动继续用旧逻辑读
    很可能直接读错。拆开存，挂载代码可以分别判断，而不是把两种性质
    不同的"变化"糊成一个数字比大小。

inode_count / data_block_count
    这个卷总共能容纳多少个 inode（等于能容纳多少个文件/目录）、
    总共有多少个数据块可用。这两个数字是 mkfs（格式化）时根据卷的
    总容量、按什么比例切分 inode 区和数据区决定的——具体切分比例
    不是 Day 29 的题目，等 Day 30 定完 inode 结构大小、以及后面
    真正写 mkfs 工具时才会给出公式；今天先把"超级块要能存下这两个
    数字"这件事定下来。

inode_bitmap_lba / data_bitmap_lba
    inode 位图、数据块位图各自的起始 LBA（卷内相对地址，含义同第一
    节）。位图是"一个 bit 对应一个 inode / 一个数据块，标记这个
    inode / 块有没有被占用"的经典分配结构——有了这两个字段，挂载代码
    不需要"猜"位图放在哪，直接从超级块读出来定位，这也是为什么这两
    个字段必须放在超级块里而不是写死在代码常量里：万一以后 Day 30
    定下 inode 结构大小后，两个位图的位置要跟着重新计算，只要 mkfs
    写的时候把算好的值填进超级块，挂载代码完全不用改。

feature_compat / feature_incompat / feature_ro_compat
    这三个字段不是 Day 29 任务清单里点名要的字段，是"关于 LMFS"
    milestone 一节里明确建议现在就加上的："只要在 Day 29 定义超级块
    时做好...你的 LMFS 就留足了未来 10 年的升级后路"。三者含义各不
    相同：
      - feature_compat：可选特性标志。驱动看不懂某一位也没关系，
        照常读写，只是用不上那个新特性。
      - feature_incompat：不兼容特性标志。驱动看到自己不认识的位，
        必须拒绝挂载——因为这意味着磁盘上的数据布局用了这个驱动
        看不懂的规则（milestone 里举的例子：v2.0 的 LMFS_FEATURE_EXTENTS，
        旧驱动如果硬挂载，会把 extent 编码的块列表当成传统的逐块
        列表来解析，读出一堆垃圾地址）。
      - feature_ro_compat：只读兼容标志。驱动不认识就只允许只读
        挂载，禁止写入——防止旧驱动用旧逻辑写坏新特性用到的数据
        结构，但至少还能把数据读出来、不影响"能不能看到文件"。
    这三个字段今天全部设为 0（本版本 v1.0 没有用到任何可选/不兼容
    特性），但位置先占好，v2.0 引入 Extents 时才有地方放标志位，
    不需要改超级块结构体本身（不改结构体大小/布局，就不会让"新
    mkfs 格式化的卷"和"老驱动"在结构对齐上直接对不上）。

reserved[476]
    补齐到 512 字节的预留空间，全部初始化为 0。跟 fat_common.h 系列
    文件一路示范的风格一致：预留字节不是"浪费"，是"以后加字段（比如
    milestone 提到的日志区起始 LBA、用户 ACL 权限指针）时，直接切一段
    reserved 用，不用挪动前面任何一个已有字段的偏移量"——旧版本格式化
    的卷、新版本的驱动，只要新字段是从 reserved 里切出来的，双方对
    "前面那些字段在哪"的理解永远一致，不会出现"新驱动以为 inode_count
    在偏移 8，实际上因为中间插了新字段变成偏移 12"这种错位。

四、Day 29 明确不做的事（留给之后）
================================================================================

  - 不定义块大小（block size）——Day 30 的任务（milestone 一节写明
    v1.0 用 1024 字节/块，但那是 Day 30 定 inode 结构时一起定的，
    今天的超级块字段里也确实没有 block_size，先不提前加，保持跟
    计划里 Day 29 的字段清单一致）。
  - 不定义 inode 表起始 LBA / 数据区起始 LBA——这两个位置依赖
    inode_count、inode 结构大小（Day 30 才定）才能算出来，今天超级块
    里也确实只要求了两个位图的位置，没要求这两个。
  - 不写 lmfs.h / lmfs.c、不写 mkfs 工具——今天的产出就是这份文档，
    代码从 Day 31 起才会陆续出现。
  - 不涉及日志（Journaling，milestone 里的 v3.0）、B+树目录、xattr——
    都是 v2.0/v3.0/v4.0 才做的事，v1.0 阶段（Day 29~84）故意不做，
    避免一开始就把简单能跑的东西做复杂。

五、验收
================================================================================

本文档本身就是 Day 29 的验收物——存在 doc/lmfs.txt，写清楚了：
魔数 0x4C4D4653、版本号（拆成 major/minor）、inode 数量、数据块
数量、inode 位图起始 LBA、数据块位图起始 LBA 六个必需字段，外加
预留的 feature flags 和 reserved 空间；并且说明了"LBA 1"是卷内
相对地址、不会跟现有磁盘布局（loader.bin 占据绝对 LBA 1~5）冲突。

Day 29 不产出可执行代码、不修改磁盘镜像、不涉及内核/引导逻辑，
因此没有可以在 QEMU 里跑起来验证的东西——今天的"跑通"就是这份
文档能自洽地回答"超级块长什么样、每个字段干什么用"。Day 30 设计
完 inode 结构后，Day 31 起才会有真正需要在 QEMU 里跑的代码。


================================================================================
六、块大小定义：1024 字节
================================================================================

DAY30 (第二月 · 第5周 · Day 30):
  "设计 inode 结构（lmfs_inode_t）：包含文件大小、创建时间、直接块
   指针 8 个 + 间接块指针 1 个 + 二级间接块 1 个（支持大文件）。
   验收：定义块大小 1024 字节（适合软盘/小硬盘）。"

块大小（block size）是"数据区最小分配单位"，inode 里的每一个块指针
指的都是"第几个这么大的块"，所以设计 inode 之前必须先把这个数定下来
——这也是为什么 Day 30 的验收标准反而是"定义块大小"，而不是"inode
结构定义完成"：块大小是 inode 设计能成立的前提，不是附带产出。

选 1024 字节（而不是跟磁盘扇区一样的 512，或者现代硬盘常见的 4096）：

  - 512 字节等于 1 个扇区，块粒度太细：一个稍大点的文件（比如几十
    KB）光是直接块 8 个（8×512=4KB）就远远不够，马上就要走间接块，
    小文件也占不到什么便宜。
  - 4096 字节对软盘（1.44MB）这种小容量介质浪费太明显：哪怕只存一个
    10 字节的文件，也要占掉一整个 4KB 块，milestone 里明确写了 v1.0
    "适合软盘/小硬盘"，4096 不合适。
  - 1024 字节（= 2 个扇区）是折中：小文件浪费可控，8 个直接块就能
    覆盖 8KB 以内的绝大多数配置文件/小文本，同时配合间接块/二级间接
    块也能支持到几十 MB 的大文件（具体算式见下一节）。

    #define LMFS_BLOCK_SIZE 1024   /* 字节 */

    块号与 LBA 的换算关系：LMFS 里"块号 N"对应卷内 LBA = N * 2
    （因为 1 个块 = 1024 字节 = 2 个 512 字节扇区）。挂载/读写代码
    统一通过这一个换算点转换，不会出现有的地方按扇区数、有的地方
    按块数直接混用的问题。

================================================================================
七、inode 结构 lmfs_inode_t（设计稿，非最终代码）
================================================================================

    typedef struct {
        uint32_t file_size;      /* 文件实际大小，单位：字节           */
        uint32_t created_time;   /* 创建时间戳（见下方字段详解）        */
        uint8_t  type;           /* 0=空闲 1=普通文件 2=目录（见详解）  */
        uint8_t  reserved0[3];   /* 补齐到 4 字节对齐，暂不使用         */
        uint32_t direct[8];      /* 8 个直接块指针                     */
        uint32_t indirect1;      /* 一级间接块指针                     */
        uint32_t indirect2;      /* 二级间接块指针                     */
        uint8_t  reserved1[12];  /* 预留，补齐到 64 字节                */
    } lmfs_inode_t;               /* sizeof == 64 字节                 */

字节偏移表：

    偏移量        大小   字段
    ------------  -----  --------------------
    0x00 (0)      4      file_size
    0x04 (4)      4      created_time
    0x08 (8)      1      type
    0x09 (9)      3      reserved0（对齐用）
    0x0C (12)     32     direct[0..7]（每个 4 字节 × 8）
    0x2C (44)     4      indirect1
    0x30 (48)     4      indirect2
    0x34 (52)     12     reserved1
    ------------  -----  --------------------
    总计          64     字节

    为什么定成 64 字节而不是"字段用多少算多少"（实际字段只用了
    52 字节）：64 能被块大小 1024 整除（1024 / 64 = 16），意味着
    inode 表里每个块恰好装 16 个完整的 inode，不会出现"第 16.5 个
    inode 跨在两个块中间"这种要拆两次读写才能拼出一个完整 inode 的
    麻烦情况。这跟超级块补齐到 512 字节（正好 1 个扇区）是同一个
    思路：让"结构大小"和"底层存储单位"对齐，访问逻辑最简单。

================================================================================
八、字段详解
================================================================================

file_size
    文件当前的真实字节数（不是占用了多少块——最后一个块通常用不满，
    file_size 记的是精确字节数，读文件时用它决定最后一块要读多少
    字节，而不是整块都当作有效数据）。

created_time
    预留的创建时间戳字段，类型先定为 uint32_t（足够存经典 32 位
    Unix 时间戳，到 2106 年才溢出，v1.0 阶段够用）。本项目目前
    没有 RTC（实时时钟）驱动——fat_common.h 里 FAT 的 DIR_*Time
    字段就是因为同样的原因，一直只能写 0（该文件注释原话："this
    project having no real-time clock driver yet, 0 is a legal, if
    uninformative, timestamp"）。LMFS 沿用同一个约定：字段先占好
    位置，Day 31 起 mkfs/lmfs_create() 实际写 inode 时先统一填 0，
    等以后哪天加了 RTC 驱动，只需要改"填什么值"这一行，不需要改
    inode 结构、不需要处理"老文件没有时间戳"的兼容问题（反正从
    v1.0 第一个 inode 开始就已经有这个字段了，只是值不准而已）。

type（补充字段，不在 Day 30 原始字段清单里，见下方说明）
    Day 30 任务描述本身只列了"文件大小、创建时间、直接块指针、间接
    块指针"，没提字段区分"这是文件还是目录"。但 Day 31 的验收标准
    是"...创建根目录 inode"——根目录本身就必须是一个 inode，而且
    必须能被认出"这个 inode 代表的是目录，不是普通文件"，否则
    Day 34 lmfs_readdir()、Day 42 多级目录解析都无法判断"该往哪个
    inode 里找子目录项"。所以这里把 type 字段提前加进 Day 30 的
    inode 设计里，取值约定为：0 = 该 inode 槽位空闲未使用（配合
    inode 位图，位图说"没占用"时这里也应该是 0，两者一致），
    1 = 普通文件，2 = 目录。如果你希望这个区分留到更后面的 Day
    （比如单独用一天设计目录项格式时再加），告诉我，我把这个
    字段挪到 reserved 里去，现在先按"现在加，免得 Day 31 卡住"
    的思路处理。

direct[8]（8 个直接块指针）
    每个是一个块号（配合第六节的换算关系，块号 × 2 = 卷内 LBA），
    直接指向存数据的块，不需要多绕一层。8 个直接块 × 1024 字节 =
    8192 字节——这是"零额外开销"就能表示的文件大小上限，绝大多数
    小文件（Shell 脚本、配置、短文本）一个间接块都用不上，读写时
    inode 里直接就是块号，少一次额外的磁盘读。

indirect1（一级间接块指针）
    指向"一个块"，这个块里存的不是数据，而是 1024 / 4 = 256 个
    uint32_t，每个是一个数据块的块号——相当于给 direct 数组续了
    256 格。所以通过一级间接块能多表示 256 × 1024 = 262144 字节
    （256 KB）。读取时要先读这一个"索引块"，再按里面某一项去读真正
    的数据块，比直接块多一次磁盘 I/O，但只有文件大小超过 8KB 才会
    用到。

indirect2（二级间接块指针）
    指向"一个索引块"，这个块里的 256 个 uint32_t 每一个又指向另一个
    "一级索引块"（跟 indirect1 指向的那种块结构完全一样），那些
    一级索引块里的 256 个指针才是真正的数据块。所以二级间接块能
    表示 256 × 256 × 1024 = 67108864 字节（64 MB）。读取时要先读
    二级索引块，再读它指向的某个一级索引块，再读数据块，一共三次
    额外 I/O 才能定位到数据——只有巨大文件才会用到这一层，符合
    milestone 里"支持大文件"的要求，但访问代价也最高，这是所有
    经典 Unix 风格 inode（ext2 等）都用这套"直接+间接+二级间接"
    分级结构而不是"全用间接块"的原因：小文件走最快的路径（直接
    块，0 次额外 I/O），只有真正的大文件才承担多级索引的开销。

    单个 inode 能表示的最大文件大小 = 直接块 + 一级间接 + 二级间接：

        8192 + 262144 + 67108864 = 67,379,200 字节 ≈ 64.26 MB

    对"软盘/小硬盘"场景（milestone 原话）完全够用，且实现复杂度
    停在"三级索引"，不需要 ext2 那样的三级间接块。

reserved0[3] / reserved1[12]
    跟超级块的 reserved 字段同一个道理：reserved0 纯粹是把 type
    这 1 个字节补齐到 4 字节边界（让紧跟着的 direct[8] 数组从 4
    字节对齐的偏移开始，x86 按 4 字节对齐访问 uint32_t 效率更好、
    也更不容易在未来移植到对齐要求更严格的架构时出问题）；
    reserved1 是给以后加字段用的余量（比如 milestone v4.0 提到的
    xattr 指针、或者以后想加的"修改时间/访问时间"跟 created_time
    放在一起），加进去不需要挪动前面任何已有字段的偏移，逻辑跟
    Day 29 超级块 reserved 字段的理由完全一样。

九、结合超级块：现在可以说清楚的卷整体布局
================================================================================

有了块大小（1024 字节）和 inode 大小（64 字节）之后，LMFS 卷内部
从头到尾的区域顺序可以完整地写出来了（具体每个区域各占多少块，
取决于格式化时选定的 inode_count / data_block_count，由 Day 31
的 tools/mkfs.lmfs 按卷总容量算出来，今天只定顺序，不算具体数字）：

    卷内 LBA 0     ：保留扇区（本阶段占位不用，见第一节）
    卷内 LBA 1     ：超级块（lmfs_superblock_t，Day 29）
    往后           ：inode 位图（大小 = ceil(inode_count / 8) 字节，
                     起始 LBA 记在超级块 inode_bitmap_lba 里）
    再往后         ：数据块位图（大小 = ceil(data_block_count / 8)
                     字节，起始 LBA 记在超级块 data_bitmap_lba 里）
    再往后         ：inode 表（inode_count 个 lmfs_inode_t，每块
                     16 个，共 ceil(inode_count / 16) 个块；这个区域
                     的起始位置本文档不新增字段去存——通过
                     "data_bitmap_lba + 数据块位图占用的块数" 直接
                     算出来，不需要在超级块里再存一个 inode_table_lba，
                     减少一个"两处数据要保持一致"的冗余字段）
    再往后（到卷尾）：数据区（存放所有文件/目录的实际内容，就是
                     direct/indirect1/indirect2 里的块号所指向的
                     地方）

    inode 编号约定：inode 0 = 根目录（对应 Day 31"创建根目录 inode"、
    Day 33 验收"能读取 inode 0"——这两条合在一起说明根目录就是 0 号
    inode，这里把这个约定明确写下来，Day 31 mkfs 和 Day 32/33 的
    lmfs_mount()/lmfs_read_inode() 都按这个约定实现，不需要再另外
    找地方存"根目录 inode 号是几"）。

十二、目录项格式：lmfs_dirent_t（Day 34 补充设计）
================================================================================

DAY34 (第二月 · 第5周 · Day 34 of the 5.0 filesystem roadmap):
  "实现 lmfs_readdir()。" 验收："能列出根目录。"

  Day 30 第十节明确把目录项格式留到"更后面的实现阶段"，理由是当时
  inode 结构本身不关心数据块里存的是文件内容还是目录项。但 Day 34
  要"列出根目录"，没有目录项格式就无从谈起——这里补上这份设计，
  仍然更新在这份文档里（而不是另开一份新文档），因为它跟超级块/
  inode 一样是 LMFS 磁盘格式的一部分，都属于"文件系统长什么样"这同
  一份规范。

文件名长度：不沿用 FAT 的 8.3
--------------------------------------------------------------------------
计划.md 文末「LumaOS 9.0 目录架构规范（权威/最终版）」是全文档目录
结构的唯一权威定义，里面出现的目录/文件名——"Administrator"（13
字符）、"TaskManager.sw"/"FileManager.sw"（14 字符）、"SystemInfo.sw"
（13 字符）等——已经超出 FAT 8.3 格式（8+3=11 字符）能装下的范围。
LMFS 是 LumaOS 自己的原生文件系统，没有理由继承 FAT 的历史限制，
所以目录项的文件名字段直接设计成"够长的定长字符串"，而不是像 FAT
那样短名+扩展名分开存、还要处理大小写折叠这些历史包袱。

目录项结构 lmfs_dirent_t（64 字节，跟 inode 同样大小，同样的理由：
能整除块大小，1024/64=16，一个块正好装 16 个目录项）：

    typedef struct {
        uint32_t inode_num;      /* 这个目录项指向的 inode 号        */
        uint8_t  used;           /* 0=空闲(未使用/已删除) 1=已使用   */
        uint8_t  name_len;       /* 名字实际字符数，不含结尾 NUL     */
        uint8_t  reserved[2];    /* 对齐/预留                        */
        char     name[56];       /* NUL 结尾，最长 55 个字符          */
    } lmfs_dirent_t;              /* sizeof == 64                    */

字节偏移表：

    偏移量        大小   字段
    ------------  -----  --------------------
    0x00 (0)      4      inode_num
    0x04 (4)      1      used
    0x05 (5)      1      name_len
    0x06 (6)      2      reserved
    0x08 (8)      56     name
    ------------  -----  --------------------
    总计          64     字节

用独立的 used 字段，而不是像 FAT 那样把"名字第一个字节"兼职当空闲
标记（0x00=结束、0xE5=已删除）：因为 LMFS 的文件名是真正的变长文本，
理论上第一个字符是任何 ASCII 字符都合法（虽然目前 mkfs.lmfs 从不
生成以特殊字符开头的名字），不能像 FAT 那样牺牲名字的某个字节位置
去表达元信息。used=0 就是空闲/已删除，used=1 就是已使用，逻辑上更
干净，代价只是每条目录项多花 1 个字节——对已经把 inode/dirent 都
定成 64 字节、本来就有富余对齐空间的 LMFS 来说完全不算什么。

数据块号 0 是保留哨兵值
--------------------------------------------------------------------------
inode 的 direct[]/indirect1/indirect2 都需要一个"这个指针槽位没有
指向任何块"的表示方式。参照"inode 0 永远有意义、代表根目录"这个
已有约定的反面：**数据块号 0 永远没有意义，代表指针为空**，真正能
分配给文件/目录内容的数据块号从 1 开始。mkfs.lmfs 格式化时会在数据
块位图里把第 0 位直接标记为已占用（永久保留，不属于任何 inode）；
Day 36/37 设计位图分配算法时，也要遵守"永远跳过块号 0"这条规则。

这个决定现在才提出，是因为直到 Day 34 要往根目录里真正写一个数据块
之前，"块号 0 到底能不能被分配"这个问题都不会被触发——但既然现在
触发了，就要一次性定下来，不能拖到以后每次遇到"这个指针是 0，到底
是'合法的块号 0'还是'没有块'"时才现场猜。

根目录内容：mkfs.lmfs 现在会往里面写什么
--------------------------------------------------------------------------
Day 31 当初生成的根目录是完全空的（file_size=0，不占用任何数据块）
——这在"能列出根目录"这个验收标准下无法验证 lmfs_readdir() 真的在
正确解析目录项，只能验证"空目录返回 0 条"这一种情况。所以 mkfs.lmfs
现在给根目录分配了块号 1（LMFS_ROOT_DIR_BLOCK_NUM）作为它的第一个
数据块，写入两条固定的目录项：

    "."   -> inode 0（根目录指向自己）
    ".."  -> inode 0（根目录的父目录约定为自己，跟大多数 Unix 系统
                       "根目录是自己的父目录"的约定一致）

根目录 inode 相应更新：file_size = 1024（1 个块），direct[0] = 1，
direct[1..7]/indirect1/indirect2 全部是 BLOCK_NONE(0)。目录的
file_size 在这里的含义是"已经分配了多少字节的块装目录项数据"（即
已分配块数 × 块大小），不是"实际写了多少字节的有效目录项"——块内
没用到的槽位（这里是 16 个槽位里的 14 个）靠 used=0 标记为空闲，
不需要 file_size 精确到字节；这跟"目录的 file_size 按块对齐"是绝大
多数经典 Unix 文件系统的通行做法一致，也让 lmfs_readdir() 的实现
可以简单地"扫描 inode 声明的每一个已分配块，逐槽位看 used"，不需要
用 file_size 做字节级别的边界截断。

十四、数据块分配器：lmfs_alloc_block()（Day 36 补充设计）
================================================================================

DAY36 (第二月 · 第6周 · Day 36 of the 5.0 filesystem roadmap):
  "实现数据块 bitmap 分配器。" 验收："连续分配多个块，bitmap 正确变化。"

Day 29 设计超级块时就已经把 inode_bitmap_lba/data_bitmap_lba 两个
字段放进去了，但一直到 Day 36 之前，从没有任何代码真正"分配"过一个
数据块——mkfs.lmfs（Day 31/34）往位图里写的两个已占用位（块号 0 的
保留哨兵值、块号 1 的根目录数据块）都是格式化时直接手工摆进去的，
不是通过某个分配器函数走出来的。Day 36 补上这第一个真正的分配器。

扫描算法：逐扇区读数据块位图（起始 LBA 就是超级块里的
data_bitmap_lba，扇区数由"ceil(data_block_count/8) 再 ceil 到整数
扇区"这条公式算出——跟 lmfs_mount() 算 inode_table_lba 用的是同一条
公式，Day 36 把它从 compute_inode_table_lba() 内部提出来，单独做成
一个 compute_data_bitmap_sectors() 共用），按"字节 -> 位"两级线性
扫描，遇到第一个值是 0 的 bit 就是找到的空闲块。全 0xFF 的字节整体
跳过、不逐位判断——位图里"已经用掉一大片"是最常见的形状（一个卷从
头开始一路分配下去，位图前半段迟早会变成连续的 0xFF），这个小优化
让扫描不用为每一个已经确定用满的字节再拆开看 8 次。

块号 0 的保留哨兵值（doc 第十二节）在这里体现为一条防御性判断：正常
情况下这一位永远是 1（mkfs 格式化时就已经标记死），分配器扫描时
天然就会跳过它，不需要专门去处理；但仍然显式加了一条"就算查到
block_num==0，也直接跳过"的检查——这不是因为今天的代码路径会用到，
而是给以后（Day 41 空间回收）留一道安全网：万一哪天释放数据块的代码
出现 bug，不小心把这一位清成了 0，分配器这边的显式检查能防止把块号
0 真的分配出去，不然会立刻在所有以"0 表示没有这个块"为前提的代码
（lmfs_readdir() 判断 direct[i]==LMFS_BLOCK_NONE 时停止扫描、未来
Day 39 write() 判断某个指针槽位是否已经用过）里制造出真假难辨的
"到底是没有块还是真的分配了块 0"的歧义。

写回范围：只写位图里真正翻转了那一个 bit 所在的扇区，不是整张位图
——数据块位图可能跨好几个扇区（虽然本项目默认的软盘大小测试卷只有
1 个扇区），没必要每次分配都把其余没变化的扇区也重写一遍，属于
"只持久化真正改动的部分"这一贯穿全项目的原则（跟 Day 23
fat_alloc_cluster() 只写回受影响的 FAT 扇区是同一个道理）。

范围之外，留给以后：
  - 不清零新分配的块内容——磁盘上原来是什么就是什么，谁用这个块
    存有意义的数据，谁负责按自己的需要清零，分配器本身不做这个假设
    （比如 create() 出来的空文件、还是 write() 要追加数据，对"要不要
    先清零"的需求不一样，不该由分配器替调用者预先决定）。
  - 不把分配到的块号填进任何 inode 的指针字段——分配器只回答"哪个
    块现在空着、我把它标记成你的了"，至于这个块最终挂在哪个文件/
    目录的 direct[]/indirect1/indirect2 上，是 Day 38/39 调用方自己
    的事。
  - 不提供释放（分配的反向操作）——Day 41（"delete() 与空间回收"）
    才会实现，今天只做分配，不做回收，避免这两个天然成对但验收标准
    分属不同 Day 的功能挤在一天里，重复 Day 22（只找）/Day 23（找
    并分配写回）当初把"找"和"分配"拆成两天的同一种克制。

十六、inode 分配器：lmfs_alloc_inode()（Day 37 补充设计）
================================================================================

DAY37 (第二月 · 第6周 · Day 37 of the 5.0 filesystem roadmap):
  "实现 inode 分配器。" 验收："创建 inode 后返回合法 inode 号。"

结构上几乎是 lmfs_alloc_block()（Day 36）原样复制一份，字段换成
inode 位图/inode 表：同样的字节->位两级线性扫描、同样全 0xFF 字节
整体跳过、同样只写回真正翻转了的那一个位图扇区。但有一处跟数据块
分配器不一样，而且是这一节真正要讲清楚的地方。

为什么数据块分配器"只翻位图、不管内容"，inode 分配器却不能这样做
--------------------------------------------------------------------------
Day 36 第十四节说得很明确：lmfs_alloc_block() 分配出一个数据块后，
块里原来是什么字节就留着，不负责清零或初始化——因为数据块的内容
本身没有"这块是不是空闲"的自描述字段，空闲与否完全由位图单独记录，
两者不会互相矛盾。

但 inode 不是这样。Day 30 设计 inode 的 type 字段时（第八节），
当时就定下了一条不变式："type==LMFS_TYPE_FREE(0) 要跟位图里这一位
是 0 保持一致"——也就是说，一个 inode 到底是不是"空闲"，从一开始
就有两套记录：inode 位图的那一个 bit，和 inode 表项自己的 type
字段。mkfs.lmfs（Day 31）格式化时两者是同步的：0 号 inode 位图置 1、
type 写 DIR；其余 inode 位图是 0、type 也是 FREE(0)。

如果 lmfs_alloc_inode() 照抄 lmfs_alloc_block() 的做法、只翻位图、
不碰 inode 表项内容，分配完之后就会出现位图说"已分配"、但这个
inode 自己的 type 还停在 FREE(0) 的局面——Day 33 的 lmfs_read_inode()
读出来的 type 会继续说"这是空闲槽位"，跟位图记录的状态自相矛盾。
所以 lmfs_alloc_inode() 必须比 lmfs_alloc_block() 多做一步：分配
的同时，把 inode 表里这个槽位的内容写成一个"刚分配、空的、属于
调用者指定 type"的合法 inode（file_size=0、created_time=0、8 个
直接块指针和两个间接块指针全部是 0——内容上跟 mkfs.lmfs 里
build_free_inode() 产出的空槽位几乎一样，唯一区别是 type 不是
FREE，是调用者要的 FILE 或 DIR）。

为什么要有 type 参数
--------------------------------------------------------------------------
分配出来的 inode 最终是文件还是目录，分配器自己不可能知道——只有
调用者知道（Day 38 的 create() 会传 LMFS_TYPE_FILE；将来如果做
mkdir 一类操作会传 LMFS_TYPE_DIR）。所以 lmfs_alloc_inode() 的签名
里加了一个 type 参数，必须是 LMFS_TYPE_FILE 或 LMFS_TYPE_DIR 之一
——传 LMFS_TYPE_FREE 或任何其他值直接拒绝：分配出一个"空闲"的
inode 这件事本身自相矛盾，调用者传这个值大概率是用法错误。

写盘顺序：先 inode 内容，后位图
--------------------------------------------------------------------------
函数内部先把 inode 表项的新内容写成功，最后才把位图那一位置位并
写回磁盘——不是反过来。这个顺序是刻意的：如果 inode 表那一步写盘
失败，位图仍然停在"未分配"状态，调用者看到的只是一次干净的分配
失败；如果反过来先写位图、再写 inode 内容，一旦 inode 内容那一步
失败，就会留下"位图说这个号已经分配、但 inode 内容其实是上一个
使用者的旧数据（或者 mkfs 时期的全零）"这种更隐蔽、更难排查的
不一致状态——两种失败都不完美（都没有真正的事务/回滚机制，这个
项目目前没有日志，见 doc 开头"关于 LMFS"milestone 提到的 v3.0
日志特性，v1.0 阶段不做），但"干净地报错"明显好过"悄悄留下一个
看起来已分配、内容却是错的 inode"。

范围之外，留给 Day 38
--------------------------------------------------------------------------
lmfs_alloc_inode() 分配完、返回一个合法 inode 号之后，这个 inode
在磁盘上是"存在但没有任何目录项指向它"的状态——跟 lmfs_alloc_block()
分配完一个块、但没有任何 inode 的指针字段指向它是同一种"孤立"状态。
把这个新 inode 的号码和一个文件名绑在一起、在某个目录的数据块里
真正写一条 lmfs_dirent_t，是 Day 38（"实现 create() 与目录项"）的
任务，不是今天。

十八、create()：lmfs_create()（Day 38 补充设计）
================================================================================

DAY38 (第二月 · 第6周 · Day 38 of the 5.0 filesystem roadmap):
  "实现 create() 与目录项。" 验收："create test.txt 成功。"

Day 32~37 攒了一整套底层能力——挂载、读 inode、列目录、分配数据块、
分配 inode——但从来没有一个函数把这几样真正串起来用过一遍。Day 38
的 lmfs_create() 就是第一个这样的函数：给一个父目录 inode 号和一个
文件名，分配一个新 inode，在父目录的数据里找个地方登记这个名字，
两者关联起来，变成一个真正"存在、能被 ls 看见"的文件。

两条路径：已有空位 vs 需要新分配一个块
--------------------------------------------------------------------------
父目录的数据块里，16 个 dirent 槽位用不满是常态（mkfs.lmfs 当初
给根目录分配的第一个块，16 个槽位只用了 2 个），所以 create() 第一
件事是扫一遍父目录现有的全部块，找有没有空闲槽位（used==0）——
如果有，新文件就"挤"进这个空位，不需要分配新块，也不需要碰父目录
自己的 inode（file_size/direct[] 都不变）。

只有父目录现有的块全部用满了，才需要走另一条路：找父目录 direct[]
里第一个还是 LMFS_BLOCK_NONE 的指针槽位，分配一个新数据块，把新
dirent 放进这个新块的第 0 个槽位，更新父目录的 direct[]/file_size。
如果父目录 8 个直接块也全部用满（128 个 dirent 槽位，doc 第十二节
提过的上限），才真正报"目录满了"——这是 v1.0 直接块限制自然带来的
副作用，跟 lmfs_readdir() 只扫 direct[] 的范围限定是同一件事的另一面。

为什么重名检查要扫完父目录全部块，不能找到空位就提前退出
--------------------------------------------------------------------------
空闲槽位和重名条目可能分别出现在父目录的不同块里——空位在第 1 个
块，重名的文件却在第 3 个块。如果扫描一找到空位就提前停下来，会
漏查后面块里的重名，造成同一个父目录下出现两个同名文件（这是
"查重"和"占位"两件独立的事，必须都做完整，不能用一次扫描的提前
退出互相替代）。所以 create() 的第一遍扫描是纯只读的：不管找没
找到空位，都要把父目录全部已分配的块看一遍，确认没有任何一条已
使用的 dirent 跟新名字完全相同，才会往下走。

LMFS 的重名判断是精确匹配，不像 FAT 8.3 那样强制转大写
--------------------------------------------------------------------------
FAT 的 8.3 短名在存盘前会被统一转成大写，所以 "test.txt" 和
"TEST.TXT" 在 FAT 卷上是同一个文件、建第二个会被判重名拒绝。LMFS
从 Day 34 起就选择了不做这层归一化（长文件名本来就是区分大小写的
普通文本），所以 "test.txt" 和 "Test.txt" 在 LMFS 上是两个不同的
文件，create() 的重名检查用的是逐字节精确比较（先比 name_len 是否
相等，再比内容），不会把大小写不同的名字当成同一个文件。

写盘顺序：资源分配在前，父目录"官宣"在后
--------------------------------------------------------------------------
两条路径里，真正改动磁盘之前，第一遍扫描+校验全部是只读的——名字
不合法、父目录不是目录、重名、父目录彻底满了，这几种情况下函数
不会留下任何副作用。校验通过后，第一步永远是分配新 inode（两条
路径都需要这个号码），这一步失败的话前面的只读扫描还没产生任何
后果。如果走的是"新分配一个块"这条路径，块内容（新 dirent + 其余
15 个槽位清零）要先写成功，父目录 inode 的 direct[]/file_size 更新
要放在最后——这样如果父目录那一步写盘失败，磁盘上只是多了一个
"内容正确、但还没有任何 inode 指向它"的孤立块（不是数据损坏，只是
暂时没被引用，这个项目目前没有日志/事务机制，不打算为这类边界情况
加回滚），不会出现"父目录已经指向某个块、那个块里其实是半成品
内容"这种更难排查的不一致——跟 Day 37 lmfs_alloc_inode() 的"先
inode 内容、后位图"是同一个指导原则在不同场景下的应用。

二十、write()：lmfs_write()（Day 39 补充设计）
================================================================================

DAY39 (第二月 · 第6周 · Day 39 of the 5.0 filesystem roadmap):
  "实现 write()，支持直接块与间接块。" 验收："写入 10KB 文件并验证。"

为什么验收标准特意选 10KB
--------------------------------------------------------------------------
8 个直接块一共只能装 8192 字节，10KB(10240 字节) 比这个数字多出
2048 字节，必须要用上一级间接块（indirect1）才能装下——这不是随手
选的数字，是故意卡在"直接块不够用、必须走间接块这条路径"的门槛
之上，逼着 lmfs_write() 把 Day 30 当初设计、却一直没人真正用过的
indirect1 字段落到实处。只支持一级间接块，不支持二级（indirect2）
——翻遍计划.md 全文 91 天，没有任何一天真正要求实现二级间接块的
读写，LMFS_MAX_FILE_SIZE（8 个直接块 + 256 个一级间接块指针，约
264KB）是本函数能写的硬上限，超过直接拒绝。

整个覆盖，不是追加
--------------------------------------------------------------------------
跟 fat_write()（Day 25）的语义完全一致：lmfs_write() 永远从字节
偏移 0 开始覆盖整个文件，新的 file_size 就是调用时传的 size。这不是
LMFS 自己的随意选择，是沿用这个项目 Shell `write` 命令（kernel/
shell/cmd/write.c）一直以来的既定含义——两种文件系统上 `write` 该
表现一致，不该因为底层实现不同就有不同的语义。

块分配顺序：数据块 -> 间接索引块 -> inode，全部在内存里先攒好再落盘
--------------------------------------------------------------------------
写入过程中，新分配的块号先全部累积在内存里（direct[] 数组、间接块
自己的 256 项索引表），每一个数据块的内容单独确认写盘成功之后才算
数；等所有数据块都写完，才把间接索引表的内容写盘；最后一步才把
inode 的 file_size/direct[]/indirect1 整个覆盖并写回。这个顺序保证
了任何一步中途失败，磁盘上的旧 inode 内容原封不动（新分配、已经
写了内容的块会变成孤立/浪费，但不会出现"inode 已经指向某个块、
那个块其实是写了一半的内容"这种更难排查的状态）——延续 Day 37
"先 inode 内容、后位图"、Day 38"先数据块内容、后父目录指针"同一条
主线的写盘顺序原则。

已知、刻意保留的限制：覆盖旧内容会泄漏旧的块
--------------------------------------------------------------------------
这是今天最值得明说的一点：对一个已经写过内容的文件（direct[]/
indirect1 已经指向真实数据块）再调用一次 lmfs_write()，本函数不会
去释放旧内容占用的块——它们会变成"磁盘上存在、但没有任何 inode 再
指向它们"的垃圾，永久占用空间，直到这个卷被重新格式化。这不是
疏忽，是刻意照抄 fat_write() 自己的历史：fat_write() 在 Day 25~26
就是这个行为（"总是分配一条全新的簇链，旧链整个泄漏"），一直到
Day 27 专门用一次更新、靠当时已经实现的 fat_truncate() 共享的释放
逻辑才修好（见 fat_vfs.h 里 fat_write() 声明上方"DAY27 UPDATE"那段
注释，记录了这整个"先上线、后面专门回头修"的过程）。LMFS 现在还
没有任何函数能释放数据块——那是 Day 41（"delete() 与空间回收"）
才会实现的能力，Day 39 没有办法提前解决这个问题，只能跟 FAT 当年
一样先把 write() 能用这件事做出来，等 Day 41 落地后再回头补上
"覆盖旧内容时先释放旧块"这个修复，用的也会是到时候跟 delete() 共享
的同一套释放逻辑。

没有把 Day 39 接进交互式 `write` 编辑器命令
--------------------------------------------------------------------------
kernel/shell/cmd/write.c 是一个已经叠了好几层历史修复、专门针对 FAT
路径写的多行交互式编辑器（光标移动、Delete/Backspace、多行缓冲区
……），今天的验收标准（"写入 10KB 文件并验证"）本身也更适合用一次
程序化的数据完整性验证来满足——写一段可核对的已知内容、再逐字节
读回来比对，而不是真的在交互式编辑器里手打 10KB 文本。所以 Day 39
的验证走的是 kmain.c 内核自测段，直接调用 lmfs_write()（以及给 Shell
以后用的路径版 lmfs_vfs_write()，kernel/fs/lmfs/lmfs_vfs.c），没有
去改 write.c 本身——把 LMFS 接进交互式 `write` 命令，留给以后专门
改 write.c 的时候再做，本函数和 lmfs_vfs_write() 已经把它需要的底层
能力备好了。

顺带新增的小工具：lmfs_lookup()
--------------------------------------------------------------------------
lmfs_vfs_write() 需要"给一个文件名，找到它的 inode 号"这个操作——
这正是 lmfs_create() 内部查重名那段扫描逻辑的只读子集，所以把它
单独抽成了 lmfs_lookup()（fs, parent_inode_num, name, out_inode_num）。
可以预见 Day 40 的 lmfs_read() 路径解析也会需要同一个操作，不该在
每个地方各写一遍相同的目录扫描代码。

二十二、read()：lmfs_read()（Day 40 补充设计）
================================================================================

DAY40 (第二月 · 第6周 · Day 40 of the 5.0 filesystem roadmap):
  "实现 read()。" 验收："read bigfile.txt 正常。"

返回值约定是这个模块里唯一的例外
--------------------------------------------------------------------------
lmfs.h 这个模块到今天为止的每一个函数——mount/read_inode/readdir/
alloc_block/alloc_inode/create/write——全部是"0=成功，-1=失败"。
lmfs_read() 故意不跟这个惯例：它返回"真正读到几个字节"（0 到 size
之间的任意值），只有负数才表示出错。原因是读操作天然存在"合法的
部分结果"——请求读 1000 字节，文件从当前位置到末尾只剩 300 字节，
读回 300 字节不是错误，是正确答案；0/-1 这套二元约定表达不了"读到
了，但没读满你要求的那么多，这是正常情况"。这正是 fat_read()
（Day 19）当年选择同一种返回值设计的理由——而且两种文件系统的
fs->read() 要塞进同一个 vfs_read_fn 函数指针槽位（kernel/fs/vfs/
vfs.h）给 Shell 的 `read` 命令统一调用，本来就必须遵守同一份契约，
LMFS 没有另起一套的余地，直接照抄这个返回值约定是唯一合理的选择。

一级间接块只读一次，不是每跨一个块都重读
--------------------------------------------------------------------------
一次 lmfs_read() 调用如果跨越了第 8 个块（需要从一级间接块的索引表
里查后续的块号），索引表只会被读进内存一次、缓存在函数内部，后续
每一个落在间接范围内的块都直接查这份缓存，不会每次都重新发一次
磁盘读。这是个小优化，但也顺带回答了一个容易被忽略的问题：如果
一次读涵盖了好几个属于间接范围的块（比如读跨度很大、从第 9 个块
一路读到第 20 个块），这个优化让读间接块索引表的磁盘 I/O 只发生
一次，不会随着跨越的块数线性增加。

跟 Day 39 lmfs_write() 共享同一套"块号定位"逻辑，但方向相反
--------------------------------------------------------------------------
"给一个字节偏移，换算成第几个块、块内第几个字节，块号 < 8 查
direct[]，否则查间接索引表"——这套定位算法 lmfs_write() 写的时候
已经用过一次（只是那边是"分配新块、顺便记下块号"，这边是"按已有的
块号去读"），两个函数各自实现了一份，没有强行抽成共享函数——写和
读终究是两个不同方向的操作，一个要处理"这个位置还没有块，需要
分配"，另一个假设块已经存在、只是找出来读，勉强共用反而会让两边
的代码都要处理对方不需要处理的分支，不如各自保持简单。

顺带新增的 lmfs_vfs_open_path()，对应 Shell `read` 命令的调用方式
--------------------------------------------------------------------------
Shell 的 `read` 命令（kernel/shell/cmd/read.c）自己一直是"几乎完全
通用"的实现——打开之后的整段读循环、关闭，全部走 vfs_node_t/file_t
的通用函数指针（fs->open/fs->read/fs->close），这是 Day 18 设计 VFS
抽象时就定下的样子。唯一不通用的只有最开头那一步：Day 18 的
fat_open() 是专属 FAT 的路径解析函数。Day 40 给 LMFS 配上同样角色的
lmfs_vfs_open_path()（kernel/fs/lmfs/lmfs_vfs.c），read.c 只需要在
最开头加一个"这个挂载点是不是 LMFS"的判断去决定调哪一个——后面那一
整段读循环代码一行都不用改，自动对 LMFS 生效。这跟 Day 38 创建文件
时 create.c 需要的改动形状完全一样（fat_create_file() 专属 FAT，
lmfs_vfs_create() 是对应的 LMFS 版本，dispatch 发生在 create.c
而不是任何一个文件系统自己的代码里）。

LMFS 上，只因为它从 Day 18 起就是照着 VFS 的通用接口写的。

二十四、delete() 与空间回收：lmfs_delete()（Day 41 补充设计）
================================================================================

DAY41 (第二月 · 第6周 · Day 41 of the 5.0 filesystem roadmap):
  "实现 delete() 与空间回收。" 验收："rm 后空间恢复。"

今天要做两件事：一是新增 lmfs_delete()（连带 lmfs_free_block()/
lmfs_free_inode() 两个分配器的反向操作）；二是回去把 Day 39
lmfs_write() 文档里明说过的"覆盖已有内容会泄漏旧块"这个已知限制
补上——两件事用的是同一套释放逻辑，自然放在同一天做。

操作顺序为什么跟 fat_delete_file() 刻意相反
--------------------------------------------------------------------------
这是今天最重要的一个设计决定，完整论证写在 lmfs.h 里 lmfs_delete()
声明上方的注释里，这里只摘要结论：FAT 的目录项自己就存着簇链起点
（DIR_FstClusHI/LO），是"可见性标记"和"数据指针记录"合二为一的
唯一记录，所以 fat_delete_file()（Day 26）必须先释放簇链、最后才
标记目录项删除——反过来做，目录项一旦被标记删除，簇链起点这个
唯一记录就丢了。

LMFS 把这两个角色拆开了：目录项只存"名字 -> inode 号"，真正的
数据块指针存在 inode 表里，靠 inode 号就能直接找到，不依赖目录项
是否还在。这意味着 lmfs_delete() 可以、而且应该先清目录项，再释放
数据块和 inode——如果反过来，一旦在"inode 已经释放、目录项还没清"
这一步中途失败，这个已经被释放、位图显示空闲的 inode 号就可能被
后续某次 lmfs_create() 重新分配给一个全新、完全无关的文件，而旧的
目录项还继续指着这同一个 inode 号——两个不同名字的文件暗地里共享
一个 inode，是真正的数据混淆，不只是空间泄漏。先清目录项，这个
问题就不存在：目录项一旦清掉，这个 inode 号在被成功释放、重新
分配出去之前，没有任何路径能再找到它，后续任何一步失败最多是
"这块空间该收回没收回"（已知、可接受的泄漏），不会是两个文件共享
一个 inode 这种更严重的问题。

这也是为什么"同一个原则，两种文件系统的具体选择却正好相反"——FAT
和 LMFS 都在遵守同一条更根本的规则："先释放/处理有用的数据，再
销毁指向它的唯一路径"，只是 FAT 的"唯一路径"（簇链起点）长在目录项
里，LMFS 的"唯一路径"（inode 号）长在 inode 表里、目录项只是其中
一条可以被安全地第一个清掉的引用——两边具体顺序不同，是因为两种
磁盘结构把"指针记录"和"可见性标记"揉在一起还是分开这件事不一样，
不是谁的设计更"对"。

释放 inode 的两个反向操作：lmfs_free_block()/lmfs_free_inode()
--------------------------------------------------------------------------
分别是 lmfs_alloc_block()（Day 36）/lmfs_alloc_inode()（Day 37）的
镜像：lmfs_free_block() 只清数据块位图里的一个 bit，不碰块的内容
（跟 alloc 方向"不保证新块内容是什么"对称）；lmfs_free_inode() 既
清 inode 位图的 bit，也把 inode 表项内容整个重置成空闲状态（type
变回 FREE、其余字段清零）——"内容先、位图后"，跟 lmfs_alloc_inode()
走的是同一条顺序规则，分配、释放两个方向共用一条规则，不用分别
记两条。块号 0（保留哨兵值）和 inode 号 0（根目录）都被这两个释放
函数显式拒绝——永远不会有人意外把它们"释放"掉。

共享的 free_inode_data()：delete() 和 write() 的共同需要
--------------------------------------------------------------------------
"把一个 inode 现在指向的全部数据块（direct[8] + indirect1 索引表
里的每一项 + indirect1 索引块自己）还给位图"这件事，lmfs_delete()
（删除一个文件）和 lmfs_write()（覆盖一个已有内容的文件之前）都
需要，所以抽成了一个内部共享的静态函数 free_inode_data()——跟
fat_free_cluster_chain_by_variant() 被 fat_delete_file()/
fat_truncate()/fat_write() 三处共用是同一个"不重复写同一套释放
循环"的理由。lmfs_write() 现在的行为：开始分配任何新块之前，先用
free_inode_data() 把这个 inode 原来占用的块（如果有的话）释放干净
——Day 39 文档里记录过的那个"覆盖会泄漏旧块"的已知限制，到这里
正式修掉。

二十六、多级目录与路径解析：lmfs_mkdir() / lmfs_resolve_path()（Day 42 补充设计）
================================================================================

DAY42 (第二月 · 第6周 · Day 42 of the 5.0 filesystem roadmap):
  "多级目录与路径解析。" 验收："可以创建并访问多级目录。"

磁盘格式一个字节都没有改
--------------------------------------------------------------------------
这是今天最值得先说的一点。Day 29~41 设计的结构里，"目录"从一开始就不是
什么特殊的东西：它就是 type==DIR 的 inode，数据块里存一串 lmfs_dirent_t
（名字 -> inode 号）。根目录和将来的任何子目录在磁盘上是【同一种东西】，
mkfs.lmfs 给根目录写的 "." 和 ".." 两条目录项（第十二节）也正是为了今天：
子目录只要照着根目录的样子再造一份，就是合法目录。所以 Day 42 不动
超级块、不动 inode、不动 dirent、不动 mkfs.lmfs，全部是"在现有格式上多写
几个函数"。这也验证了 Day 30/34 当时"目录是 inode 的一种用法，inode 本身
不关心数据块里存的是文件内容还是目录项"这条设计是对的。

前 41 天的 LMFS 为什么是"扁平"的
--------------------------------------------------------------------------
lmfs_lookup/lmfs_create/lmfs_delete 的参数是"一个目录 inode 号 + 一个纯
文件名"。它们本来就支持任意目录，是上层 lmfs_vfs.c 把父目录硬编码成
LMFS_ROOT_INODE_NUM、并且拒绝任何含 '/' 的名字，才让整个系统看起来只有一层。
Day 42 的核心工作其实只有两件：
  1. 能造出一个"非根"的目录（lmfs_mkdir）。
  2. 把 "a/b/c.txt" 这样的路径字符串翻译成"哪个目录 inode + 哪个名字"
     （lmfs_resolve_path / lmfs_resolve_parent），让 lmfs_vfs.c 不再写死根目录。

lmfs_mkdir()：目录 = inode + 数据块 + "." / ".."
--------------------------------------------------------------------------
与 lmfs_create() 共用同一个内部函数 create_node()（校验名字、查重名、
找空槽位/新分配块、把新项挂进父目录——全部一份代码），只是 type 不同。
type==DIR 时多一步，顺序是"内容先、可见性后"（跟 Day 37/38/39 同一条原则）：
  a. lmfs_alloc_inode(DIR)           分配 inode
  b. lmfs_alloc_block()              给目录自己分配 1 个数据块
  c. 在这个块里写两条目录项：
         slot 0 : "."  -> 新目录自己的 inode 号
         slot 1 : ".." -> 父目录的 inode 号
     其余 14 个槽位全 0（used=0，空闲）
  d. 把新 inode 更新成 file_size=1024、direct[0]=该块，写回
  e. 最后才把 (name -> 新 inode) 登记进父目录（走 create 的老路径）
任何一步失败，尽力把已分配的块和 inode 释放回去（best-effort，仍无事务）。
"." 和 ".." 是保留名：create/mkdir 拒绝它们，否则一个目录里会出现两条 "."，
lookup 取哪条取决于槽位顺序，是不确定行为。

lmfs_resolve_path()：一段一段 lookup
--------------------------------------------------------------------------
路径解析的本质只有一个循环：
    cur = (path 以 '/' 开头) ? 根 : 起点
    对 path 里的每一段 name：   cur = lookup(cur, name)
最后一段之前每一步 cur 必须是目录（lookup 自己会拒绝"在文件里找东西"，所以
"leaf.txt/x" 自然失败）。连续的 '/'、结尾的 '/' 被吞掉。

最漂亮的一点：解析器【不特殊处理 "." 和 ".."】。它们在磁盘上是真实的目录项，
lookup(dir, "..") 就能找到父目录，根的 ".." 指向自己所以 "/.." 还是根。"."
和 ".." 对解析器来说只是两个普通名字。这正是 Day 34 把它们做成真实目录项、
而不是解析器里的"魔法字符串"的回报——Unix 的 ext2 也是同样做法。

lmfs_resolve_parent() 只解析到倒数第二段：把 "a/b/c.txt" 拆成"目录部分
a/b -> 父目录 inode"+"最后一段 c.txt"。create/mkdir/delete 需要的是"在哪个
目录里增删哪个名字"，不是最终 inode（最后一段此时可能还不存在）。

Shell 层：当前目录 + 归一化（shell_resolve_path）
--------------------------------------------------------------------------
Day 25 的 cd 只是在挂载点之间切换（vfs_root），Day 42 给"当前目录"加了第二个
坐标：卷里面的哪个目录。shell.c 保存一个字符串 cwd（相对卷根，无首尾 '/'，
"" = 卷根），并记住它属于哪个卷（vfs_root 被别处改掉时 shell_get_cwd() 回退
成 ""，不会把旧路径配到别的卷上）。shell_resolve_path() 把用户敲的任何东西
变成 "<挂载点>/<归一化路径>"：
    第一段是已注册挂载点 (IDE3/...)  -> 全限定
    以 '/' 开头                      -> 当前卷内的绝对路径
    其它                              -> 当前卷 + cwd + "/" + 输入
然后做【文字层面】归一化：去掉空段和 ".", ".." 弹出上一段（到卷根为止，不能
爬出卷、进入别的挂载点）。LMFS 没有符号链接，文字归一化与磁盘上走 ".." 等价，
所以交给 lmfs_vfs 的路径通常已经干净；直接给 lmfs_vfs 传带 ".." 的路径也对，
因为解析器能走磁盘上的 ".."。

结果：create/read/write/rm 一行都不用改就支持了多级路径——它们早就是
"先 shell_resolve_path，再把路径交给 lmfs_vfs_*"，变的只是这两层的内部。
cd/ls 改为认目录；新增 mkdir；ls 不再显示 "./" 和 "../"（它们在磁盘上存在，
但只在显示层过滤——lmfs_readdir 仍返回它们，解析器和 Day 34 的测试依赖这点）。

已知限制（刻意不做，留给以后）
--------------------------------------------------------------------------
  - 没有 rmdir：lmfs_delete 仍只删普通文件，目录被拒绝（本日不扩展）。
  - 交互式 `write` 编辑器仍只接 FAT（Day 39 文档已说明）；LMFS 子目录里的文件
    内容目前只能由内核自测/lmfs_vfs_write 写入，shell 里能 create/read/rm。
  - 一个目录最多 8 个直接块 = 128 项（含 "." ".."）；lmfs_readdir 每次最多
    返回 32 项（LMFS_DIRLIST_MAX_ENTRIES），所以 ls 一个 >32 项的目录会被截断。
  - 目录没有链接计数/没有 mtime；路径长度受 shell 路径缓冲区（64 字节）限制。
